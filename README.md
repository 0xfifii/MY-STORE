# MY STORE — Inventory Management

A complete inventory system for a real store: items in any unit (bags, kg, litres, crates…), Stock In and
Stock Out with live balances, weighted-average stock valuation, daily / weekly / monthly reports
(PDF, Excel, CSV), low-stock alerts, a permanent transaction history with controlled corrections, staff
accounts with roles, and automatic scheduled reports.

All data lives in a PostgreSQL database. Refreshing the page, closing the browser or switching devices
never loses anything.

## 1. Deploy it (pick one)

### Option A — Render + Neon (free) — recommended

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/0xfifii/MY-STORE)

1. **Database:** sign up at <https://neon.tech> → create a project (region: AWS Europe Frankfurt) →
   **Connect** → copy the connection string (`postgresql://…`).
2. **App:** click the **Deploy to Render** button above (or render.com → **New → Blueprint** → pick this
   repo). Sign in with GitHub. When it asks for `DATABASE_URL`, paste the Neon string. Click **Deploy**.
3. Wait for **Live** (first build 5–10 minutes), open your `https://….onrender.com` address and create the
   owner account.

That's all. Tables are created automatically on start, `CRON_SECRET` is generated by Render, and the
app's built-in scheduler produces the daily / weekly / monthly reports.

Free-plan notes: Render puts a free app to sleep after 15 minutes without visitors; the next visit takes
about a minute to wake it, and any report that fell due while it slept is generated then. To keep it
always awake, create a free job at <https://cron-job.org> that calls `https://YOUR-APP/api/health` every
10 minutes. Neon's free plan includes 1 GB of storage — years of records for a single store.

### Option A2 — Vercel + Supabase

Vercel's free (Hobby) plan is limited to personal, non-commercial use, so for a store use Vercel Pro.


**Database (Supabase)**

1. Create an account at <https://supabase.com> → **New project**. Choose a region close to you (e.g. *West EU*),
   set a database password and save it.
2. When the project is ready: **Project Settings → Database → Connection string → URI**. Copy the
   **Transaction pooler** string (port `6543`). Replace `[YOUR-PASSWORD]` with your password.
3. Create the tables. On your computer (needs Node.js 20+ from <https://nodejs.org>), in this folder:

   ```bash
   npm install
   DATABASE_URL="postgresql://postgres.xxxx:PASSWORD@aws-0-eu-west-1.pooler.supabase.com:6543/postgres" npm run db:migrate
   ```

   (On Windows PowerShell: `$env:DATABASE_URL="..."; npm run db:migrate`.)
   You should see `Applying 001_init.sql … Database is up to date.`

   *No Node.js?* Open Supabase → **SQL Editor**, paste the contents of `db/migrations/001_init.sql`, run it,
   then do the same for `002_…sql` and `003_…sql`, in order.

**App (Vercel)**

4. Put this folder in a GitHub repository (github.com → **New repository** → upload the files, or `git push`).
5. At <https://vercel.com> → **Add New → Project** → import the repository.
6. Under **Environment Variables** add:

   | Name | Value |
   |---|---|
   | `DATABASE_URL` | the Supabase pooler string from step 2 |
   | `DATABASE_POOL_MAX` | `3` |
   | `CRON_SECRET` | a long random string (e.g. from <https://www.random.org/strings/> or `openssl rand -hex 32`) |
   | `APP_URL` | your Vercel address, e.g. `https://my-store.vercel.app` (you can add this after the first deploy) |

7. Click **Deploy**. Open the address Vercel gives you and create the owner account (section 2).

The included `vercel.json` runs the report job once a day at 06:15 UTC (07:15 in Lagos), which is what
Vercel's free plan allows. With the default report time (07:00, previous day) that produces yesterday's
report every morning, the weekly report on Mondays and the monthly report on the 1st. If you want a
different time or more frequent checks, either upgrade Vercel and change the schedule to `*/15 * * * *`,
or use the free GitHub Actions trigger in `.github/workflows/daily-report.yml` (add `APP_URL` and
`CRON_SECRET` as repository secrets).

> Supabase's free plan pauses a project after a week of no use (restore it from the Supabase dashboard).
> For a store used daily this doesn't happen. Upgrade to Pro for daily backups.

### Option B — Your own computer or server with Docker (everything in one command)

Works on a shop PC (Windows/Mac with Docker Desktop) or any Linux server/VPS.

```bash
cp .env.example .env          # Windows: copy .env.example .env
# edit .env: set CRON_SECRET to a long random string; add SMTP_* if you want email
docker compose up -d --build
```

Open <http://localhost:3000> (or `http://SERVER-IP:3000`). This starts:

- **db** — PostgreSQL with data stored in a Docker volume (survives restarts and updates)
- **app** — MY STORE; database tables are created/updated automatically on start
- **scheduler** — triggers the automatic reports every 15 minutes
- **backup** — a nightly database backup into `./backups` (kept 14 days)

Set `POSTGRES_PASSWORD` in `.env` before the first start. For access over the internet, put it behind
HTTPS (e.g. Caddy or Nginx with Let's Encrypt) and set `APP_URL` to the https address.

Update to a new version: replace the files and run `docker compose up -d --build` again.

### Option C — Any Node.js host (Render, Railway, a VPS…)

- Build command: `npm ci && npm run build`
- Start command: `npm run db:migrate && npm start`
- Environment variables: see section 9. Use a PostgreSQL database that is **not** set to expire
  (Render's free Postgres is deleted after 30 days — use Supabase or a paid database).
- Scheduler: call `POST https://YOUR-APP/api/cron/daily-report` with header
  `Authorization: Bearer YOUR_CRON_SECRET` every 15 minutes (host cron job, or the GitHub Action above),
  or run `npm run reports:run` from system cron.

## 2. First sign-in

1. Open the app. The first visit shows **Create the owner account** — enter the store name, your name,
   email and a password. This only works once.
2. **Store Settings**: check currency (₦ NGN by default), time zone (Africa/Lagos) and switch on the
   automatic daily / weekly / monthly reports.
3. **Users**: add a sign-in for each staff member so every stock movement records who did it.
4. **Categories** and **Suppliers**: add the ones you use (you can also add them while adding items).
5. **Add New Item** for each product, with its unit, minimum stock level and the quantity you have now
   (the opening stock). From then on, use **Stock In** and **Stock Out** — balances are never typed in by hand.

Daily use:

- **Stock Out**: search the item → enter quantity → pick the reason → Review → Confirm. You see the
  balance before and after; the app refuses to issue more than is available.
- **Stock In**: search the item → quantity, cost per unit, supplier → Review → Confirm. If the item
  doesn't exist yet, the search offers **Add “…”** and brings you back to Stock In afterwards.
- Both are also on every row of the Inventory list and on the dashboard.
- **Daily Reports**: choose Today / Yesterday / Weekly / Monthly / Date range, filter by item or category,
  then download PDF, Excel or CSV.

## 3. Automatic reports and email

In **Store Settings → Automatic reports** choose any of:

- **Daily** — the previous full day (recommended) or the same day up to the report time
- **Weekly** — every Monday, for the previous Monday–Sunday
- **Monthly** — on the 1st, for the previous month

Reports are generated on the server after the chosen time (in the store's time zone), at most once per
period and format, and kept in **Report History** for download. If a scheduled run is missed (e.g. the
server was off), the next run catches up.

**Email** is optional. Add these environment variables and redeploy, then tick *Email the automatic
reports*, enter recipients and press **Send test email**:

```
SMTP_HOST=smtp.gmail.com        # or your provider's SMTP host
SMTP_PORT=587
SMTP_USER=you@gmail.com
SMTP_PASS=your-app-password     # Gmail: Google Account → Security → App passwords
SMTP_FROM="MY STORE <you@gmail.com>"
```

Without SMTP settings nothing is emailed and Report History says *Email not set up* — it never claims an
email was sent when it wasn't.

## 4. Backups

- **Supabase**: Pro plan has daily automatic backups. On the free plan, download a backup regularly:
  `pg_dump "$DATABASE_URL" -Fc -f mystore-$(date +%F).dump`
- **Docker**: the `backup` service writes `./backups/mystore-YYYY-MM-DD.dump` every night.
  Copy that folder somewhere else (USB drive, Google Drive) regularly.
- **Restore** into an empty database: `pg_restore --no-owner -d "$DATABASE_URL" mystore-2026-10-18.dump`

Stock movement records are never deleted by the app (the database itself refuses), so a backup always
contains the complete history.

## 5. How the numbers work

- **Balances come from the ledger.** Every Stock In, Stock Out and correction is a permanent transaction.
  An item's balance is changed only by those transactions, inside a database transaction that locks the
  item row, so two people issuing stock at the same moment can't cause a wrong or negative balance.
- **Daily carry-forward.** For any period: *Closing = Opening + Received − Issued ± Corrections*, per item,
  and each day's closing balance is exactly the next day's opening balance. Every report ends with the
  per-item balance table and the most stocked in / most stocked out items for the period.
- **Units are never mixed.** Each item is counted in one unit. Other units can be used only if a rule
  exists: standard ones (1 kg = 1000 g, 1 L = 1000 ml, 1 m = 100 cm, 1 dozen = 12 pcs) or ones you set per
  item (e.g. *Rice: 1 bag = 50 kg*, *Coke: 1 crate = 24 bottles*). Anything else is refused.
- **Decimals**: quantities up to 6 decimal places (0.25 kg, 2.75 bags). Items can be set to whole units only.
- **Valuation: perpetual weighted-average cost.** A receipt adds its own quantity and cost; each issue is
  valued at the average cost of the stock on hand at that moment, and that cost is saved with the
  transaction so old reports never change when prices move. Money is kept to the kobo.
- **Most stocked in / out** is ranked by value, because quantities in different units can't be compared.
- **Corrections**: an owner can *Reverse* a wrong transaction with a reason. The original stays visible,
  a correction transaction undoes it, and it's recorded in the Audit Log.
- **Duplicate clicks** are safe: each form submission carries a unique id, so a double-click or a retry
  after a network drop records the movement only once.

## 5b. Workers, permissions and usage analysis

- **Workers** (Setup → Workers): the names of people who collect items. Pick a name under "Taken by" on
  every Stock Out; reports and Usage & Audit then show who took what.
- **Permissions** (Users → Permissions): for each staff or viewer account, tick exactly what they may do
  (Stock In, Stock Out, add items, manage workers, see usage analysis, …) and optionally limit Stock In/Out
  to certain categories. Enforced on the server.
- **Usage & Audit**: money spent on stock (big pie by item, category or supplier, with insights), the
  amount stocked in and stocked out per **day, week or month** (chart + table), most and least taken items
  (big pie), who took what, reasons, categories, which staff account recorded what, and a filterable log of
  every change. Downloadable as CSV.
- **Reports** open with a general summary (total stock value, opening value, cost of stock in, cost of stock
  out, net change, items low/out) and then one stock sheet per item: S/N, item, opening stock, stock in,
  cost of stock in, stock out, cost of stock out, closing balance (Bal) and worth — all in one table — plus
  totals by category and a single "stock in and stock out" list. Weekly/monthly reports add a day-by-day
  sheet where each day's closing is the next day's opening.
- **Deleting items**: owners (or users given "Delete items permanently") can delete an item from its card or
  its page. The item and all of its stock records are removed after a confirm step, and the deletion is kept
  in the change log. To only hide an item and keep its history, use Archive.

## 7. Running locally and tests

Requirements: Node.js 20+ and PostgreSQL 14+.

```bash
npm install
cp .env.example .env.local      # set DATABASE_URL (and CRON_SECRET)
npm run db:migrate
npm run dev                     # http://localhost:3000
```

Optional sample data for trying things out (**empty demo database only**): `npm run db:seed-demo`
(login `demo@mystore.local` / `demo-pass-123`).

Tests:

```bash
npm test                 # fast unit tests
npm run build
npm run test:e2e         # full acceptance suite: creates a throwaway local database "mystore_test",
                         # starts the app and a local mail server, and checks all 18 acceptance criteria
python3 tests/ui_walkthrough.py http://localhost:3000 ./screenshots   # browser walkthrough (Playwright),
                                                                     # phone/tablet/desktop, empty DB
```

The acceptance suite covers: adding items; 10 bags in, 2.5 out → 7.5; 20 + 5.5 − 3.25 = 22.25 kg;
weighted-average costing; over-issue refusal; unit mixing refusal and valid conversions; persistence;
daily totals; reconciliation (yesterday's closing = today's opening); CSV/Excel/PDF contents; search;
permissions for every role; double-submits and 30 simultaneous stock-outs; scheduled daily/weekly/monthly
reports with real email delivery; reversals; and that every page loads.

## 8. Project structure

```
db/migrations/        SQL schema, stock functions (stock_in, stock_out, reverse_transaction), reference units
src/app/(app)/        Pages: dashboard, inventory, items, stock-in/out, transactions, reports, settings…
src/app/api/          JSON API used by the pages (all validated and permission-checked server-side)
src/lib/inventory.ts  Item and transaction queries
src/lib/reports/      Report engine + CSV / Excel / PDF builders + scheduler
src/components/       UI (stock form, item picker, item form, tables, dialogs)
scripts/              migrate, demo seed, scheduled-report trigger, test helpers
tests/                unit, acceptance (API + DB) and browser walkthrough tests
```

Stack: Next.js 15 (App Router, TypeScript), PostgreSQL, Tailwind CSS, pdfmake, ExcelJS, nodemailer.

## 9. Environment variables

| Variable | Required | Purpose |
|---|---|---|
| `DATABASE_URL` | yes | PostgreSQL connection string |
| `CRON_SECRET` | for automatic reports | Shared secret the scheduler sends as `Authorization: Bearer …` (16+ characters) |
| `APP_URL` | recommended | Public address of the app |
| `DATABASE_POOL_MAX` | no | Connections per server instance (default 10; use 3 on Vercel) |
| `DATABASE_SSL` | no | `false` to turn off SSL for private/local databases |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, `SMTP_SECURE` | for email | Email delivery of automatic reports |

Secrets are only read on the server and are never sent to the browser.
